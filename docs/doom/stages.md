# Stages

Each row: what it is, the tests that hold it, the demo that runs it, and where
its numbers live. Nothing starts before the row above it is green.

The project used to carry two tracks — a home robot and a Doom player — on one
platform. Only the Doom player is left; the vacuum, the kit car and everything
built for them live in the git history up to `1bf247a`.

| 21 | **Search over the worm's proposals.** Built and tested (`learning/search.py`, `tests/test_search.py`, `scripts/search_probe.py`); the measurement is what remains. With noise the brain is a distribution, not a function: sample N intents from one state, roll each forward 10-20 ticks in a copy of the world, keep the best. The connectome is the proposal distribution, the rollout is the judge. First question, before anything else: does this improve play at all? If it does not, there is nothing to teach | | | next |
| 22 | **The competence map.** Log (state, the N proposals, the one chosen) over many episodes and ask where the worm is already right: the fraction of ticks where its modal proposal is the chosen one, sliced by situation — target ahead, wall between, monster on the flank, stuck. This answers "what is this architecture good at" by situation instead of by one reward number | | | after 21 |
| 23 | **Distillation, and the question it settles.** Train the weights to make the chosen action likelier — expert iteration, the way search-generated targets train a network. Then benchmark the worm *alone*, with no search at runtime, which is the form that could go on a robot. It also separates the two things every negative result here has conflated: **the architecture cannot represent this behaviour** against **our search could not find it**. If the worm can be taught what the rollout found, the connectome could always express it | | | after 22 |
| 23b | **If the search is to teach anything, it must first be a policy.** The obvious repair: make the teacher deterministic in the state — average the top-k branches instead of taking the luckiest one, or widen the candidate set until the mean is stable — and re-run the two cheap checks in `docs/knowledge/method.md` before building anything on it | `tests/test_search.py` | | done 2026-09-19, **the repair fails and locates the fault**: averaging the best k shrinks the decision spread from 0.708 to 0.163 while the within/between ratio stays at 1.03, 0.97, 0.94, 1.03 — nothing under the noise. But the worm is not silent: the same estimator along its *own* noisy trajectory gives a signal 5× its error, against 1.3× along the search's. The demonstrations were recorded where the connectome has least to say. `SearchConfig.consensus`, `RandomProposer` and the noise-write-through fix are the code that came out of it |
| 24 | **Record the teacher where the student lives.** Drive with the student and let the search label what it should have done there — DAgger's correction for the trajectory mismatch stage 23b measured — and re-run the same-state-twice ratio on the new demonstrations before training anything | `tests/test_search.py` | | done 2026-09-19, **the loop works and the result does not**: the gate passes (0.51 against the control's 1.02, so the labels *are* a function of the state), and at 4800 evaluations instead of 480 the student beats a constant for the first time in this project (0.1579 against 0.1639). It then plays 0.29 where the untaught brain plays 0.31, on 20 unseen maps, and the self-distillation control scores 0.26 — the look-ahead taught nothing. Expert iteration is closed with each stated reason eliminated in turn |
